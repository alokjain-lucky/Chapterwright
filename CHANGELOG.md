# Changelog

All notable changes to Chapterwright. See [README.md](README.md#changelog) for the most recent entries — this file is the full history.

### 2.9.1

- **Fixed a crash right after adding a chapter in the Books & Chapters admin app.** Reported live: the new chapter was created fine (correct ID and meta, visible on refresh), but the screen immediately broke with a minified React error — "object with keys `{raw, rendered, protected}`". `addChapter()`'s success handler appends the create request's response object straight into `chapters` state rather than re-fetching (deliberate — a re-fetch right after create can lag behind on some hosts, per the comment already in `book-detail.js`). That response comes from core's own `/wp/v2/hsrtech_chapter` POST endpoint, whose `excerpt` field is the standard `WP_REST_Posts_Controller` `{ raw, rendered, protected }` shape — every *other* chapter in the list comes from `getBookChapters()` (the plugin's own `chapterwright/v1` route), whose `excerpt` is a plain string (`get_the_excerpt()`). The chapter row's `chapter.excerpt && ... { chapter.excerpt }` assumed the plain-string shape and rendered the raw object directly as a React child, which is exactly what that error means. `chapter.title` already tolerated both shapes at its two render sites (`chapter.title?.raw || chapter.title?.rendered`) for the same underlying reason; applied the identical fallback to excerpt instead of normalizing the create response upstream. Only visible on sites with "Table of contents excerpts" turned on in the admin app's chapter list.

### 2.9.0

- **Section URLs nested under their book**, moving from the flat `/section/{section-slug}/` shape 2.8.9 shipped to `/books/{book-slug}/{section-slug}/`, matching a chapter's own nested URL exactly. Chapter and Section share the identical URL shape one level under `/books/`, resolved by a single combined rewrite rule rather than two separate ones (WordPress only ever lets one of two identical-pattern rules match, so both post types are now matched together the same way core's own `'post_type' => 'any'` queries work).
- **"Start reading" now opens a book's first section's own introduction page when it has one**, instead of always linking straight to the first chapter.
- **Chapter Previous/Next navigation now includes a section's own introduction page as a stop**, not just other chapters — advancing into a chapter that starts a new section lands on that section's page first when it has content, and stepping back off that section's first chapter lands back on the section's page.
- **The floating "table of contents" button, missing from a section's own introduction page since it became a post type in 2.8.9, has been added** — same button and slide-in drawer a chapter page already has.
- **Sections now default to draft on create**, matching how a new chapter has always started. Publish a section from the Block Editor when it's ready; a draft section's own page doesn't resolve publicly and its heading doesn't yet appear in the table of contents, the same as a draft chapter.
- **Added a "Table of contents section descriptions" setting** (Settings → Reading experience, on by default) to turn a section's description on or off in the table of contents list. Turning it off only shortens the list to headings alone — the description itself is unaffected everywhere else, including on the section's own introduction page.

### 2.8.9

- **Breaking (internal data model): a book's sections are now `hsrtech_section` posts, not rows in the `hsrtech_sections` database table.** A section's post title is its table-of-contents heading and its post excerpt is the short description shown under that heading — both unchanged from before, still quick-editable inline from a book's page in the admin app — and its post content is new: an optional standalone introduction page. Existing sites migrate automatically on the first request after updating (`hsrtech_migrate_sections_table_to_posts()`, `includes/upgrade.php`): every row becomes a post with the same name/description/order, every chapter's section assignment is repointed at the new post, and the old table is dropped once every row has migrated. The migration is resumable — each row is removed from the old table immediately after its replacement post is created, not in one final sweep, so a request that's interrupted partway through only reprocesses what's actually left next time and never creates a duplicate post for a row that already succeeded.
- **Sections can now have their own introduction page.** Open a section from a book's page in **Chapterwright → Books & Chapters** ("Open in Block Editor →") and write it like a chapter — its title and excerpt are already filled in from the section's name and description. The table-of-contents heading becomes a link to that page only once it has real content; a section with nothing written stays plain heading-and-description text, exactly as before. The page follows the reader's light/dark mode and the book's own accent color, and paginates like a chapter page too — "Next" leads into the section's first chapter and "Previous" leads back to whatever chapter came right before it in the book, rather than only offering a way back to the table of contents.
- **Chapter URLs moved from the flat `/book-chapter/{slug}/` to `/books/{book-slug}/{chapter-slug}/`, nested under their book.** Computed from each chapter's current book at request time, so it's always correct with nothing stored to migrate. An old bookmarked `/book-chapter/{slug}/` link still resolves, redirected to the new URL by WordPress core's own slug-history mechanism (`wp_old_slug_redirect()`) — not something this plugin had to build.
- Table-of-contents section headings now use the same link styling as a chapter row — no underline, just the book's accent color on hover — instead of a plain, browser-default underlined text link.
- A section's Block Editor screen now participates in the same "click of back returns to the right book" behavior a Book or Chapter's already has, instead of landing on a near-empty native list screen.
- The public table of contents now only ever shows published sections — a draft, pending, private, or scheduled section's heading no longer appears there, matching how draft chapters already worked. No known exploit; found during a defense-in-depth review prompted by this plugin's past WordPress.org review feedback. Every admin-facing view of a book's sections (the admin app, its automation abilities) is unaffected and still shows every status.
- Hardened the update process itself: the section migration above is now safe to retry after a partial failure (a row already migrated is never reprocessed or duplicated), and every future schema/data migration follows the same version-gated, resumable pattern.

### 2.8.8

- **Added a `chapterwright/note` block** for highlighting a note, warning, or tip inside a chapter: an editable label (`RichText`, plain text only) above one or more `core/paragraph` blocks via `InnerBlocks`, restricted to paragraphs and pre-filled with one via `template`/`allowedBlocks`. A static block (`blocks/note/block.json`, `edit.js`, `note.php`) — `save()` produces the actual front-end markup directly, since there's no server-computed data to fold in at render time, so no `render.php` is needed. Styling (`blocks/note/style.css`) reuses the same `--hsrtech-paper`/`--hsrtech-ink`/`--hsrtech-line`/`--hsrtech-accent` custom properties as the rest of the reader and the existing `.hsrtech-callout` "highlighted margin note" convention (accent-colored left border, paper background), so a note tracks the reader's light/dark toggle and each book's own accent color automatically. Every `var()` carries a literal fallback since the stylesheet auto-loads on any page containing the block, not only book/chapter pages. Kept deliberately restrained after a couple of rounds of visual polish — a tinted background and a glow ring around the label's dot marker both ended up feeling like too much next to a full page of reading, so the shipped version is a plain paper background, a thin accent border, and a small solid accent dot.

### 2.8.6

- **Added a "Right offset" setting for the floating table of contents button**, alongside the existing "Bottom offset" added in 2.8.5 (Settings → Reading experience → Button position). Same pattern: a `toc_button_right_offset` number field (0-500px, clamped in `hsrtech_sanitize_settings()`), a `hsrtech_toc_button_right_offset()` getter, and a `--hsrtech-toc-jump-right-offset` custom property. `assets/css/chapterwright.css`'s two `.hsrtech-toc-jump` rules now compute `right` as `calc(2rem + var(--hsrtech-toc-jump-right-offset, 0px))` / `calc(1.25rem + var(--hsrtech-toc-jump-right-offset, 0px))` instead of a flat value, so a site can nudge the button horizontally too — not just vertically — when another floating element overlaps it from the side rather than from below. `public/assets.php` combines both offsets' `wp_add_inline_style()` output into a single `:root { ... }` block, only emitting the properties that are actually non-zero.
- **Fixed the `chapterwright/list-books` Abilities API ability returning a `chapter_count` that could include chapters the caller isn't allowed to see**, flagged by a WordPress.org plugin review. `hsrtech_ability_list_books()` counted every chapter returned by `hsrtech_get_all_chapters_for_admin()`, which deliberately returns every chapter under a book regardless of author or status — but a book and its chapters are separate capability types, so being allowed to list a book doesn't mean the caller can see every chapter under it (e.g. a book with chapters drafted by other authors). Now filters chapters to `current_user_can( 'edit_post', ... )` per chapter before counting, matching the same check already used by `hsrtech_ability_get_book_overview()` and the `GET /books/{book_id}/chapters` REST route.

### 2.8.5

- **Added a "Button position" setting for the floating table of contents button** (Settings → Reading experience), reported live: a site owner's theme added its own floating "Buy me a coffee" widget in the same bottom-right corner as `.hsrtech-toc-jump`, overlapping it. Rather than a one-off CSS fix for that specific widget, added a general "extra space above the button" number field (`toc_button_offset`, 0-500px, clamped in `hsrtech_sanitize_settings()` mainly to stop a typo from pushing the button off-screen) so a site owner can nudge it clear of *any* other floating element sharing that corner — a chat widget, a cookie banner, or anything else a theme or another plugin adds there — without editing CSS at all. `assets/css/chapterwright.css`'s two `.hsrtech-toc-jump` rules (desktop and the `@media (max-width: 720px)` override) now compute `bottom` as `calc(2rem + var(--hsrtech-toc-jump-offset, 0px))` / `calc(1.25rem + var(--hsrtech-toc-jump-offset, 0px))` instead of a flat value — the `var(…, 0px)` fallback is what keeps every site that never touches the new setting at exactly today's position, with zero extra CSS output. `public/assets.php` only calls `wp_add_inline_style()` to actually set `--hsrtech-toc-jump-offset` on `:root` when `hsrtech_toc_button_offset()` is non-zero, so a site that leaves the field at its 0 default gets nothing extra in `<head>` either.

### 2.8.4

- **Fixed "Highlight lines" not matching the line numbers actually shown in the gutter once "Start line" was anything other than 1.** Reported live: setting Start line to 15 and wanting the rows displayed as 18-20 highlighted required typing "3-5" instead — the number counted from the top of the snippet, not the number on screen. Root cause: `hsrtech_parse_code_snippet_line_ranges()`/`parseLineRanges()` (client-side mirror, `assets/js/code-highlight.js`) always parsed the raw field into a set keyed by position-from-the-top (1, 2, 3, …), which every rendering path then checked with `index + 1` — deliberately independent of "Start line" by original design, on the theory that adjusting where the gutter starts counting from shouldn't force an author to redo their highlight ranges. In practice that read as broken, not convenient, since an author looks at the rendered gutter and types the number they see. Fixed at every render path by checking the highlight set against `startLine + index` instead of `index + 1` — the same expression each path already used to compute the *displayed* gutter number, so "Highlight lines" and the numbers on screen are now guaranteed to agree by construction: `blocks/code-snippet/render.php` (the initial/no-JS server render), `assets/js/code-highlight.js`'s `buildLineRows()` (front-end re-coloring), and `blocks/code-snippet/edit.js`'s `buildPreviewElement()` (the block editor's read-only preview). `hsrtech_parse_code_snippet_line_ranges()`/`parseLineRanges()` themselves are unchanged — they just parse the raw string into a set of literal numbers either way; only what those numbers are compared against changed. Verified with start line 15 and "Highlight lines" 18-20: rows displaying 18, 19, and 20 get the highlighted modifier, confirmed via a jsdom-driven run of the actual front-end script (constructing the same `.hsrtech-code__lines`/`data-hsrtech-*` markup `render.php` outputs, letting the real `processLineRows()`/`buildLineRows()` code path run end to end) rather than reasoning about the diff alone.

### 2.8.3

- **Added a "View" action to the Books & Chapters admin app** — an icon-only button (`icon="external"`, matching the reorder-arrow icon buttons already used elsewhere in the app) in `books-list.js`'s card footer, `book-detail.js`'s title row, and each chapter row in `ChaptersManager`, opening that book or chapter's actual front-end page in a new tab. For a published book/chapter this is a plain `get_permalink()`; for anything still draft/pending/private/future, `get_permalink()` alone 404s for everyone including the author, so it's `get_preview_post_link()` instead — the same `preview`/`preview_nonce` query args core's own "Preview" button uses, only valid for the currently logged-in user, which is fine since this link is only ever clicked from inside the already-authenticated admin app. Books already had a `link` field via the core `/wp/v2/hsrtech_book` REST response, but `WP_REST_Posts_Controller` always sets it to the plain permalink regardless of status — a new `rest_prepare_hsrtech_book` filter (`hsrtech_rest_prepare_book_view_link()`, `includes/content-types.php`) swaps in the preview-aware link for anything not published, leaving published books' evergreen permalink untouched. Chapters go through the custom `chapterwright/v1` route instead of the core controller (see `admin/rest/chapters.php`'s file docblock for why), which didn't expose a `link` at all; `hsrtech_prepare_chapter_for_response()` now computes the same status-aware link directly.

### 2.8.2

- **Fixed the chapter-page table-of-contents drawer (`.hsrtech-toc-drawer`) showing long chapter titles that overflowed sideways, forcing an ugly, hard-to-use horizontal scroll to read them.** `templates/partials/toc-list.php` is the single shared partial rendering identical markup/classes for both the book page's own full-width inline `.hsrtech-toc` section and the chapter page's `.hsrtech-toc-drawer__body`. Root cause: `.hsrtech-toc-row__title { flex-shrink: 0; }` is the desktop default in `assets/css/chapterwright.css`, and the existing fix for it (`flex-shrink: 1; min-width: 0;`, the standard flexbox text-wrap pattern — `min-width: 0` is needed alongside `flex-shrink: 1` because a flex item's default `min-width: auto` independently blocks shrinking below content width) only lived inside `@media (max-width: 720px)`, a viewport-width query. The drawer is a fixed-width slide-in panel (`max-width: 26rem`, `width: 88vw`) regardless of the actual browser viewport, so on an ordinary wide desktop window (confirmed live at `window.innerWidth: 1728`) the media query never applied, even though the drawer's own container was narrow (`clientWidth: 416`) — a case of container width diverging from viewport width that a viewport-based query can't address. Verified live on production (`alokjain.dev/book-chapter/what-is-the-ai-client/`) by injecting the candidate CSS via a `<style>` tag before touching any source file, confirming `scrollWidth === clientWidth` (416 = 416) and zero overflowing rows across all 30 TOC entries. Fixed with a drawer-scoped, unconditional override: `.hsrtech-toc-drawer .hsrtech-toc-row__title { flex-shrink: 1; min-width: 0; }`, added directly below the base rule — scoped to the drawer specifically so the book page's own inline TOC keeps its existing desktop behavior untouched.

### 2.8.1

- **Fixed the Code Snippet block's frame and code `<pre>` rendering as two visibly different background shades, with unwanted top/bottom margin, outside book/chapter pages.** Root cause: `.hsrtech-code pre` never explicitly set its own `background`, and the shared rule setting `margin: 0` had the exact same CSS specificity (one class, one element) as a generic theme rule like `.entry-content pre { background: ...; margin: 1.5rem 0; }` — on a specificity tie, whichever stylesheet the browser happened to load later won, and nothing ever competed for `background` at all, so a theme's own value always applied unopposed. Rescoped every `pre`/`code` rule in `blocks/code-snippet/style.css` through both `.hsrtech-code` and `.hsrtech-code__frame` (a genuine second class, not a swap of one for another — an earlier attempt at this fix mistakenly just renamed the single class it went through, without actually raising specificity) and added an explicit `background: none`, so these rules reliably outrank a theme's single-class selector regardless of load order.
- **"Show language label" off now also reduces the code's reserved top padding**, via a new `hsrtech-code--no-lang` modifier class — previously turning the label off left the same amount of empty space reserved for it. Reduced fully in the block editor (no copy button there to still clear); reduced partially on the front end, where the copy button still needs some clearance.
- **Fixed line numbers ("Show line numbers") drifting out of alignment once a line visually wraps onto a second row** (only relevant with "Wrap long lines" also on) — the gutter was a flat, pre-generated `1\n2\n3…` list in a separate `<pre>`, which only stayed lined up with the code `<pre>`'s own rows for as long as no line ever wrapped. `assets/js/code-highlight.js`'s new `buildNumberedLines()` now regroups the same tokens the highlighter already produces into one row per source line — a number and that line's code side by side — so a wrapped line's continuation simply has no extra number instead of every later one drifting. Still tokenizes the whole snippet in one pass first (so a multi-line comment or string is recognized correctly), only changing how the result is grouped into rows afterward. The old server-rendered two-`<pre>` markup (`render.php`) is unchanged and still what a visitor with JavaScript disabled sees — the original drift limitation now applies only there.
- **Tightened a few more REST API and Abilities API permission checks**, following a WordPress.org plugin review: the `chapterwright/get-book-overview` ability and the `GET /books/{book_id}/chapters` REST route both filtered chapters only by whether the caller could edit the *book*, not each individual chapter returned — since Books and Chapters are separate capability types, both now also filter to chapters the caller can individually edit. `DELETE /sections/{id}` checked edit rights on a section's book only, even though deleting a section also unassigns every chapter in it (a write to each) — it now shares the same per-chapter check the equivalent Ability already had, pulled into `hsrtech_user_can_delete_section()` (`includes/sections.php`) so both enforce the same rule.

### 2.8.0

- **Fixed the Code Snippet block not highlighting code or having a working copy button outside of book and chapter pages.** Root cause: `assets/js/code-highlight.js` — the script that both tokenizes/colors a code block's contents and wires up the copy button's click handler — was only ever enqueued by `hsrtech_enqueue_public_assets()` (`public/assets.php`) on book/chapter/archive/shortcode pages. The block's own frame (language label, copy button chrome) always rendered correctly anywhere, since that's `block.json`'s own `"style"` registration, which auto-loads wherever the block is used regardless of post type — so a Code Snippet block used in an ordinary post looked right at a glance, but its tokens were never colored and its copy button never actually worked, since the one script responsible for both never ran. A second, compounding issue: the `--hsrtech-tok-*` color variables the token `<span>`s need lived only in `assets/css/chapterwright.css`, which has the same book/chapter/archive/shortcode-only enqueue condition — so even fixing the script's enqueue alone wouldn't have colored anything. Fixed both: `hsrtech_enqueue_public_assets()` now also loads the highlighting script (and `blocks/code-snippet/style.css`) whenever `has_block( 'chapterwright/code-snippet', $queried_id )` is true, for any post or page; and the `--hsrtech-tok-*` variables plus the `.hsrtech-tok--*` rules that use them moved from `chapterwright.css` into `blocks/code-snippet/style.css`, which — being tied to the block itself via `block.json`, not a manual page-type check — was already loading everywhere the block appears. `code-highlight.js`'s own `querySelectorAll()` was also broadened to include `.hsrtech-code pre` directly (previously scoped only to `.hsrtech-chapter__content`/`.hsrtech-book-intro` containers), so it actually finds a code-snippet block sitting in an ordinary post's content.
- **The Code Snippet block can now highlight JSON.** A sixth hand-rolled grammar in `code-highlight.js`'s `GRAMMARS`, alongside the existing PHP/JS/CSS/HTML/Shell ones — distinguishes object keys (colored as `property`) from string values via a lookahead for a following `:`, plus number/boolean-or-null/punctuation rules.
- **Added three new Code Snippet block options**, all in the block's Inspector panel (`edit.js`) alongside the existing Language/Caption fields: "Wrap long lines" (`wrapLines` attribute) shows long lines wrapped instead of behind a horizontal scrollbar; "Show line numbers" (`showLineNumbers`) adds a numbers gutter, implemented as a second, independent `<pre>` listing `1\n2\n3…` next to the code rather than per-line wrapper elements, specifically so `code-highlight.js`'s existing whole-block tokenizing pass doesn't need to become line-aware — the trade-off is that line numbers can drift out of alignment with "Wrap long lines" also on, if a source line wraps to more than one visual row; "Show language label" (stored inverted, as `hideLanguageLabel`, to avoid a double-negative "Hide X" toggle in the UI) omits the small `PHP`/`JSON`/etc. label in the block's top-left corner. All three are rendered in `render.php` via a new `.hsrtech-code__body` flex wrapper around the code (and optional numbers) `<pre>` elements.

### 2.7.0

- **Added a "Trashed books" screen to the Books & Chapters admin app.** The books list's "View trashed books" link used to send authors to wp-admin's own Books list table filtered to `post_status=trash` — a context switch to a screen this plugin doesn't otherwise use, styled completely differently. `admin/app/src/screens/trash.js` (new) lists trashed books in place, with Restore and Delete permanently actions. `admin/rest/books.php` (new) adds the two routes core doesn't expose for this: `GET /chapterwright/v1/books/trash` (a `get_posts()` query, same pattern as `hsrtech_get_all_chapters_for_admin()`) and `POST /chapterwright/v1/books/{id}/restore` (wraps `wp_untrash_post()` — core's REST posts controller can trash and force-permanently-delete a post over REST, but has no "untrash" verb). Permanent deletion reuses the existing core `DELETE /wp/v2/hsrtech_book/{id}?force=true` directly from the admin app, since core already supports that. Both new routes gate on `current_user_can( 'delete_post', $id )`, matching the capability WordPress core itself requires for the Restore/Delete Permanently row actions in its own trashed-posts list.
- **Chapters in the Books & Chapters admin app now show their number (1., 2., 3., …) in front of the title**, reflecting their current position in the list — previously only the reader-facing table of contents numbered chapters; the admin list didn't.
- **The table of contents now shows a chapter's excerpt for a draft chapter too**, when "Show excerpt in table of contents" is on and the chapter has one — previously excerpt display was published-only (`templates/partials/toc-list.php`). A draft chapter also keeps showing its real order number now instead of having it replaced by the word "Draft"; "Draft" is a separate, still screen-reader-visible label next to the title instead.
- **Chapters in the Books & Chapters admin app now show their excerpt below the title too**, for drafts and published chapters alike, matching the same "Show excerpt" setting (`hsrtech_prepare_chapter_for_response()`, `admin/rest/chapters.php`; `window.hsrtechApp.showTocExcerpt`, `admin/app.php`).
- **Fixed a chapter, section, or book occasionally staying missing from its list right after being added successfully, even after the 2.6.1 fix.** Confirmed live: clearing a server-side cache made a missing chapter reappear immediately with no other change. What looked like brief read-after-write replication lag on the host was actually a page/edge cache keying on the request URL and serving a stale response for a chapter/section/book list, regardless of WordPress core's own `Cache-Control: no-cache` header on REST responses for logged-in requests — a URL-keyed cache can simply ignore that. Every `GET` in `admin/app/src/api.js` now appends a `_ts=Date.now()` query argument, so each request is a URL the cache has never seen and can't serve a stale hit from, no matter how long its TTL is.

### 2.6.1

- **Fixed a book, section, or chapter that had already changed or been deleted server-side staying stuck in an admin app list, with every retry repeating the same error and nothing visibly changing.** Root-caused live via a WordPress.org user report + browser DevTools: deleting a section returned a 404 from `hsrtech_rest_can_edit_section()` — `hsrtech_get_section()` found nothing for that ID, meaning the section no longer existed in the `wp_hsrtech_sections` table even though it was still showing in the admin app's list (state had drifted out of sync with the server, most likely from an earlier request that actually succeeded despite the UI not reflecting it). The 2.6.0 hardening pass made that failure visible as an error banner instead of nothing at all, but didn't fix the underlying staleness — the same ghost row stayed clickable and every retry hit the identical 404. `SectionsManager`'s `saveSection`/`removeSection`/`move` and `ChaptersManager`'s `removeChapter`/`persist` (`admin/app/src/screens/book-detail.js`), plus `BooksList`'s `handleTrash` (`admin/app/src/screens/books-list.js`, found in the same audit), now all re-fetch and re-render their list after a failed request, not only after a successful one, so a stale row disappears (or a stale order snaps back to what the server actually has) the moment an action against it fails, instead of staying stuck indefinitely. `books-list.js` needed its own quiet re-fetch helper (`refreshBooksQuietly`) rather than reusing the existing `loadBooks()` for this, since `loadBooks()` starts by clearing the error message — reusing it here would have wiped the very error it was refreshing after.
- **Fixed the mirror-image bug: a newly created chapter (and, defensively, section) not appearing right after being added, with no error anywhere.** Root-caused live the same way: DevTools showed the `POST /wp/v2/hsrtech_chapter` succeeding (201, with the correct `id` and `meta` in the response), but the `GET /chapterwright/v1/books/{id}/chapters` request that `addChapter()` fired immediately afterward came back without that chapter — a brief read-after-write gap on the host, not anything wrong with what was actually saved server-side. `addChapter()` and `addSection()` (`admin/app/src/screens/book-detail.js`) no longer re-fetch the list right after a successful create; they append the object the create request already handed back directly into local state instead, which has every field the list needs (`hsrtech_prepare_chapter_for_response()`, `admin/rest/chapters.php`, already shapes chapters to match the core REST response's `{ id, title, status, meta }` structure for exactly this reason).

### 2.6.0

- **Added a "Books & Chapters" link to the plugin's row on the Plugins screen** (`hsrtech_add_plugin_action_links()`, `admin/app.php`), gated on `current_user_can( 'edit_hsrtech_books' )`, so finding the admin app doesn't require already knowing it lives under a top-level menu item.
- **The Code Snippet block's language list is no longer a fixed 6-language array baked into the editor JS.** `hsrtech_localize_code_snippet_languages()` (`blocks/code-snippet/code-snippet.php`, new, hooked on `enqueue_block_editor_assets`) builds a 22-language default list, run through the new `hsrtech_code_snippet_languages` filter, and localizes it to the block editor as `window.hsrtechCodeSnippetLanguages`; `edit.js` reads that first, falling back to the old built-in list if it's ever unset.

Added an explicit `::placeholder` rule using the block's own `--hsrtech-code-ink` variable.
- **Fixed the book cover image on a book's hero not filling the available height**, in both the block editor and the front end. `.hsrtech-book-hero__cover img` used `height: auto` inside an `align-items: center` grid, so it only ever rendered at its own intrinsic aspect-ratio height next to a taller text column.
